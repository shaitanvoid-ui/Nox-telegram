# Дополнительные проверки конкурентности и границ доверия

Эти проверки дополняют основной отчёт в [qa.md](qa.md). Они проверяют реальные
транзакции PostgreSQL, общие счётчики Redis и HTTP-контракт авторизации. Telegram
на границе тестов заменён явно обозначенным адаптером; тесты не подтверждают
доставку команд в настоящий Telegram.

## Проверенные сценарии

| Набор | Проверки | Последний результат этого набора |
| --- | --- | --- |
| `test_postgres_moderation.py` | Одинаковые и разные конкурентные наказания; конкурентная отмена; прямые команды снятия ограничений; неоднозначный ответ Telegram; устаревшее временное наказание; конфликт ключа идемпотентности; утрата прав; изоляция чатов | 10 passed |
| `test_http_auth_boundaries.py` | Выход при разном регистре Bearer; единый лимит запросов; отсутствие чувствительных данных в ошибках; 12 конкурентных вариантов одного initData; недоступность хранилища replay | 6 passed |
| `test_shield_adversarial.py` | Некорректные URL; совместная работа Anti-Spam и Anti-Flood; отсутствие потерь Redis-счётчика при 24 конкурентных сообщениях | 5 passed |

Команды запуска из корня репозитория:

```bash
NOX_TEST_POSTGRES_URL="$NOX_DATABASE_URL" \
NOX_TEST_REDIS_URL="$NOX_REDIS_URL" \
uv run pytest tests/integration -q
```

Здесь PostgreSQL должен быть доступен через `postgresql+asyncpg://`. Тестовая
роль должна иметь право создания схем. Для каждого PostgreSQL-теста создаётся
случайная отдельная схема; существующие таблицы не очищаются. Redis-тесты
счётчиков используют отдельные случайные идентификаторы чатов и удаляют свои
ключи. Replay-ключи имеют короткий TTL. Для CI рекомендуется отдельная тестовая
база и отдельный Redis. При отсутствии соответствующих переменных реальные
инфраструктурные проверки пропускаются; это не считается успешной проверкой
PostgreSQL или Redis.

В процессе эти тесты воспроизвели ошибки, исправленные до получения указанных
результатов: снятие нового наказания при истечении старого, перезапись наказаний
конкурентными действиями, несогласованный статус после `/unban` и `/unmute`,
неполный выход с `bearer` в нижнем регистре, обход лимита регистром схемы,
ошибку исполнения валидной Telegram-авторизации, двойной учёт сообщений двумя
модулями Shield и исключения при разборе некорректных ссылок.

## HTTP benchmark

`scripts/benchmark.py` отправляет настоящие HTTP-запросы запущенному API. Он
авторизуется один раз, прогревает выбранный маршрут, затем поддерживает заданное
число конкурентных клиентов. Ошибки HTTP и транспорта входят в число ошибок и
измерение задержки. Секреты авторизации не печатаются. Для рабочего аккаунта
токен передаётся через `NOX_BENCHMARK_TOKEN`; `--demo` вызывает только явно
демонстрационный вход.

```bash
uv run python scripts/benchmark.py \
  --base-url http://127.0.0.1:8001 --demo \
  --requests 300 --concurrency 10 --warmup 20 \
  --max-p95-ms 300 --output docs/benchmark-local.json
```

Требуемый бюджет для этой проверки: **0 ошибок и p95 ≤ 300 мс**. Код возврата
равен 1 при превышении бюджета или ошибках запросов, 2 — при ошибке подготовки.
Перед нагрузочным тестом нужен отдельный локальный экземпляр API с достаточно
высоким `NOX_API_RATE_LIMIT`; менять production-лимиты для этой проверки не
следует. По умолчанию выбирается Dashboard первого доступного чата. Параметр
`--path` позволяет задать другой маршрут.

На 2026-10-16 проверка выполнялась по loopback к одному процессу Uvicorn:
Python 3.12.14, PostgreSQL 17.11 в контейнере, Redis 8.10.2. Dashboard использовал
настоящие SQL-запросы и явно синтетические демонстрационные данные. Ограничитель
был повышен до 100000 запросов в минуту только в тестовом процессе. Авторизация
и прогрев исключены из времени измерения.

Первое измерение: 300/300 успешных ответов, 75,402 запроса/с, p50 102,359 мс,
p95 288,414 мс. Повтор с явно заданным бюджетом: 300/300 успешных ответов,
64,048 запроса/с, p50 114,436 мс, p95 370,115 мс. **Бюджет второго измерения не
выполнен**; исходный JSON хранит `targets_met: false`. В это время параллельно
выполнялись сборки Docker и другие проверки. Это зафиксированная базовая
нагрузочная проба в общей среде, а не контролируемый production-benchmark.

Файл [benchmark-local.json](benchmark-local.json) содержит результат последнего
запуска команды и может быть обновлён финальной проверкой после завершения
сборок. Сравнивать результаты следует вместе с параметрами, временной меткой и
нагрузкой среды. Измерения не распространяются на Telegram Bot API, реальные
мобильные клиенты, внешнюю сеть, большой объём истории и несколько процессов.
Пропускная способность обработки Telegram-сообщений этим тестом не измеряется.

Перед production нужны отдельная длительная нагрузка с репрезентативным
размером БД, проверка очереди при перегрузке, испытания реального Bot API и
Mini App на Android и iOS. Текущие проверки не заменяют эти испытания.
