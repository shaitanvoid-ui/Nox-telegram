# Развёртывание и эксплуатация

Production не публикуется автоматически. Docker Compose по умолчанию запускает изолированную локальную демонстрацию. Для реального чата нужны отдельные секреты, домен, HTTPS, проверенные миграции, Telegram-интеграция и разрешение владельца на публикацию.

## Production-конфигурация

Храните реальные значения вне Git: в секрет-хранилище, защищённых переменных окружения либо файле окружения с минимальными правами доступа. Значения `.env.example` не подходят для production.

| Переменная | Требование |
| --- | --- |
| `NOX_MODE` | `production`; demo-вход и синтетическое заполнение запрещены |
| `NOX_DATABASE_URL` | PostgreSQL через `postgresql+asyncpg://`, отдельный пароль и ограниченная роль |
| `NOX_REDIS_URL` | Закрытый Redis; аутентификация/TLS по инфраструктуре, без публичного доступа |
| `NOX_BOT_TOKEN` | Токен отдельного бота из BotFather, переданный безопасно |
| `NOX_WEBHOOK_SECRET` | Случайная строка минимум 32 символа; допустимы `A-Z`, `a-z`, `0-9`, `_`, `-` |
| `NOX_CORS_ORIGINS` | JSON-массив точных HTTPS-origin Mini App, без wildcard |
| `POSTGRES_PASSWORD` | Новый production-пароль; согласован с URL API |
| `NOX_DOMAIN` | Публичный домен Mini App для Caddy, например `nox.example.org` |

Используйте отдельную БД и бота для staging. Не копируйте пользовательские данные в demo. Проверка конфигурации при запуске предотвращает часть ошибок, но не заменяет настройку сети, TLS, резервных копий и Telegram permissions.

Разворачивайте production на отдельном хосте либо с отдельным Compose project и volumes. Смена `POSTGRES_PASSWORD` в `.env` не меняет пароль уже созданной роли внутри существующего PostgreSQL volume. Не подключайте production к demo-volume и не удаляйте ценные данные ради пересоздания пароля; ротацию выполняют управляемо в самой БД и секрет-хранилище.

## Запуск

1. Зафиксируйте проверенный commit и lockfiles. Изучите changelog и изменение схемы.
2. Сделайте резервную копию и проверьте возможность её восстановления.
3. Подготовьте production-окружение и соберите образ: `docker compose build`.
4. Примените миграции одним контролируемым процессом:

```bash
docker compose -f docker-compose.yml -f infra/compose.production.yml up -d postgres redis
docker compose -f docker-compose.yml -f infra/compose.production.yml run --rm api alembic upgrade head
docker compose -f docker-compose.yml -f infra/compose.production.yml up -d api worker web caddy
docker compose -f docker-compose.yml -f infra/compose.production.yml ps
```

В production стартовый скрипт API не выполняет seed и не применяет миграции автоматически. Это предотвращает конкуренцию нескольких web-процессов за миграцию. Сервис `bot` относится к профилю `polling` и не нужен для production webhook.

Overlay `infra/compose.production.yml` требует Docker Compose 2.24.4+ с поддержкой `!reset`. Он удаляет host-порты БД, Redis, API и web; наружу выходят только порты Caddy 80/443. Домен должен указывать на сервер, порты ACME должны быть доступны для выпуска сертификата. Caddy проксирует web, а web — `/api` в API. Изучите `infra/Caddyfile`, в том числе HSTS, до применения к своему домену. Для управляемого ingress адаптируйте этот слой под свою инфраструктуру. Параметры доверия к proxy headers задавайте для конкретного доверенного proxy.

Настройка BotFather и webhook описана в [bot.md](bot.md). Установка webhook сама по себе не добавляет бота в чаты и не предоставляет ему административные права. Сначала проверьте одну тестовую супергруппу.

## Приёмка

Проверьте `/health` и `/ready`, создание настоящей Telegram-сессии, запрет `/api/v1/auth/demo`, отказ доступа к чужому чату, реальные права инициатора и бота. Проверьте успешное и отказавшее наказание, повторный update, изменение настроек и запись аудита. Убедитесь, что UI не показывает mock-данные как настоящие.

В реальных клиентах Android/iOS отдельно проверьте safe areas, клавиатуру, BackButton, поворот/изменение viewport, сворачивание, touch targets и повторный вход после истечения сессии. Если эти проверки ещё не проведены, первая эксплуатация ограничивается тестовым чатом.

## Резервное копирование

Сохраняйте резервные копии вне репозитория и вне единственного Docker volume. Шифруйте их, ограничьте доступ, установите срок хранения и автоматическую проверку. `scripts/backup.sh` создаёт custom-format dump в игнорируемой Git директории `.backups` с закрытыми правами; затем копию необходимо зашифровать и перенести в отдельное хранилище. Следующий ручной пример сохраняет dump вне дерева проекта; выберите уникальное имя, чтобы не перезаписать предыдущую копию:

```bash
mkdir -p ../nox-backups
docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > ../nox-backups/nox-before-upgrade.dump
```

Восстановление сначала выполняется в новой тестовой базе:

```bash
docker compose exec -T postgres sh -c 'createdb -U "$POSTGRES_USER" nox_restore_test'
docker compose exec -T postgres sh -c 'pg_restore -U "$POSTGRES_USER" -d nox_restore_test --no-owner --no-privileges' < ../nox-backups/nox-before-upgrade.dump
```

После восстановления проверьте таблицы, количество записей, миграцию, запуск API и критичный сценарий. Пример не удаляет действующую базу. Для реального восстановления остановите запись, определите допустимую потерю данных, согласуйте переключение и только затем меняйте production-подключение. Для малого RPO настройте управляемые PostgreSQL backup/PITR; один `pg_dump` не обеспечивает восстановление до произвольной секунды.

Redis содержит временные данные и не заменяет резервную копию PostgreSQL. Потеря replay-ключей может изменить окно защиты от повторного входа; процедуру аварийного восстановления нужно учитывать при управлении сессиями.

## Сроки хранения

Параметр чата `privacy_retention_days` регулирует журналы Shield и Audit; worker удаляет записи старше выбранного срока. История наказаний и апелляций сохраняется отдельно. После обработки update его исходный payload очищается, а минимальный receipt с ID остаётся для дедупликации. Старые pending updates не должны исполняться как новые команды; текущий worker завершает их как устаревшие через двое суток.

Запущенный API без worker не выполняет фоновую очистку. Настройка срока журналов не означает автоматическое удаление всех данных пользователя и backup. До реального использования определите политику архивации receipts, наказаний, апелляций и резервных копий, а также процедуру запроса на удаление.

## Обновление и откат

Запускайте CI и миграцию на копии базы до изменения production. Совместимость старого приложения с новой схемой проверяется отдельно. Возврат предыдущего контейнера безопасен только при совместимой схеме; `alembic downgrade` не является универсальным откатом.

Не удаляйте Docker volumes и историю Git как способ обновления. Настройте наблюдение за ошибками API/Telegram, latency, размером очереди, отказами БД/Redis и запасом диска. Для дел `unknown` требуется проверка фактического состояния Telegram до повторного действия. Сырые сообщения, токены и `initData` не должны записываться в мониторинг.

## GitHub и CI/CD

CI проверяет код без production-секретов. Публикацию на реальный сервер можно добавить отдельным workflow с GitHub Environment и required reviewers после решения владельца. Этот проект не включает неявное автоматическое развёртывание в production.

Если GitHub недоступен, выполняйте те же команды локально и не называйте их успешным запуском GitHub Actions. Создание remote и push подтверждаются отдельно наличием файлов и статусом workflow на GitHub.
