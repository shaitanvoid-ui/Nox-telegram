# Подключение Telegram

Бот, HTTP API и Mini App используют один `ModerationService` и PostgreSQL.
Внешние действия разрешены только в `NOX_MODE=production`. Режим `demo` использует
явный `DemoTelegramGateway`: изменения записываются в демонстрационную БД, но
сообщения и наказания в Telegram не отправляются.

## Первый запуск

1. Создайте бота в официальном `@BotFather` командой `/newbot`.
2. Запишите токен в локальный `.env`, переменная `NOX_BOT_TOKEN`. Не передавайте
   токен в URL, командной строке, issue, чат разработки или исходном коде.
3. Настройте PostgreSQL (`NOX_DATABASE_URL`), Redis (`NOX_REDIS_URL`),
   `NOX_MODE=production`, явные HTTPS `NOX_CORS_ORIGINS` и случайный
   `NOX_WEBHOOK_SECRET` длиной не менее 32 символов.
4. Выполните миграции: `uv run alembic upgrade head`. Запустите API и
   `uv run python -m nox.worker`.
5. Добавьте бота в supergroup администратором. Выдайте права удаления сообщений
   и ограничения участников. Для просмотра всех сообщений отключите Group
   Privacy в BotFather, если это соответствует политике сообщества.
6. Из личного профиля администратора выполните `/setup` в группе. Astra проверит
   администратора через Telegram, сохранит чат и его роль. Каждый администратор,
   которому нужен доступ к Mini App, выполняет `/setup`. Повторная команда не
   сбрасывает настройки. Анонимные администраторы не поддерживаются.
7. Задайте HTTPS адрес Mini App через BotFather `/setmenubutton`. Авторизация
   Mini App проверяет сервером подписанные `initData`; `initDataUnsafe` не
   предоставляет полномочия.

Настройку HTTPS webhook выполните на своей инфраструктуре через метод Bot API
`setWebhook`: URL `https://YOUR_DOMAIN/api/v1/telegram/webhook`, `secret_token`
равен `NOX_WEBHOOK_SECRET`, `allowed_updates` — `message`, `edited_message`,
`my_chat_member`. Не вставляйте токен в shell-историю или логи. Автоматического
production-развёртывания и автоматической регистрации webhook нет.

Для локального polling с настроенным production-окружением:

```bash
uv run python -m nox.bot
uv run python -m nox.worker
```

Polling удаляет webhook без удаления ожидающих updates. Не запускайте несколько
polling-процессов одного бота. `python -m nox.bot` принимает updates, worker
обрабатывает их; без worker команды остаются в очереди.

## Команды модерации

Отправляйте команду ответом на сообщение участника:

| Команда | Поведение |
| --- | --- |
| `/warn причина` | Предупреждение в БД; по умолчанию каждые три предупреждения — мут на 60 минут |
| `/unwarn причина` | Отмена последнего действующего предупреждения |
| `/ban [7d] причина` | Постоянная или временная блокировка |
| `/unban причина` | Разблокировка; не удаляет уже вступившего участника |
| `/mute 30m причина` | Временное ограничение отправки сообщений |
| `/unmute причина` | Восстановление текущих стандартных прав чата |
| `/kick причина` | Удаление из группы с возможностью вступить снова |

Срок: от 1 минуты до 365 дней; `m`/`м`, `h`/`ч`, `d`/`д`. Причина обязательна,
3–1000 символов. Владелец, администраторы, сам бот и сам модератор защищены от
наказания. Проверяются локальная роль, текущая роль Telegram, права ограничений
модератора и бота. Ошибка или таймаут Telegram не выдаются за успех.

Временные ban/mute используют встроенный `until_date` Telegram и обслуживаются
worker. Ручной unmute восстанавливает текущие стандартные права группы; снимка
старых индивидуальных ограничений эта версия не сохраняет.

## Shield и Studio

Flood/Spam — общий атомарный счётчик Redis; Duplicate хранит хеш текста,
Link и Mention — конкретные фильтры сообщений. Scam, сообщения ботов,
подозрительные изменения и всплески вступлений создают события для проверки.
Рейд не является основанием наказать всех новых участников. По умолчанию
включены Flood, Duplicate и Scam; фильтр всех ссылок включается явно.

Если Redis недоступен, временные счётчики отключаются без наказания пользователя,
остальные фильтры работают. Если не удалось проверить статус Telegram участника,
автоматическое удаление не выполняется. Текст сообщения в ShieldEvent не хранится.

Правила Studio исполняются по событиям: вступление → приветствие;
флуд → удаление/мут; порог предупреждений → мут. Автор правила сохраняется
сервером. При каждом выполнении проверяются его текущие права. Уникальный ключ
события исключает повторное исполнение, события из действий не запускают новые
правила. Начатое действие с неизвестным результатом не повторяется автоматически.
Если предупреждения обработало правило Studio, стандартная эскалация не дублируется.

Автоматический Emergency Mode с изменением прав всего чата пока не реализован:
сначала нужны сохранённый снимок разрешений, проверка изменений администратора
и проверенный протокол восстановления. Всплески вступлений создают уведомления
в журнале Shield, без изменения прав группы.

## Доставка и восстановление

HTTP webhook проверяет секрет и подтверждает update только после фиксации
`ProcessedUpdate`. Polling сдвигает offset после фиксации. Worker атомарно
резервирует update до исполнения. После обработки исходный payload удаляется;
ID receipt сохраняется для дедупликации. Старые необработанные updates через
двое суток получают `failed / queue_expired`, чтобы не исполнять устаревшие
команды. Сбой после внешнего действия даёт `unknown`: проверьте Telegram и
историю дела вручную, вместо слепого повтора.

Минимальные receipts с ID хранятся без срока удаления. Нужна отдельная политика
архивирования при больших объёмах. Срок хранения журналов Shield и Audit
задаётся на чат; worker очищает их. История наказаний сохраняется для апелляций.
Временные окна Redis автоматически истекают.

## Проверки этой версии

Интеграция Telegram проверена контролируемыми ответами API: успешные вызовы,
права, повторная доставка, отрицательный ответ, rate limit и неоднозначный
сетевой сбой. Реальный bot token и реальный Telegram-клиент в среде разработки
не предоставлены; отправка сообщений в настоящий чат не проверена.
