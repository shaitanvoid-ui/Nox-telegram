# Архитектура NOX

NOX — модульный монолит: API, обработчики Telegram и фоновые операции используют одну предметную модель и PostgreSQL. Mini App — отдельный React-клиент. Разделение процессов позволяет независимо масштабировать HTTP и обработку событий без распределения бизнес-логики по микросервисам.

Эта версия создаёт проверяемую основу продукта. Полная AI-модерация, все защитные модули, социальная система и production-развёртывание не считаются готовыми только из-за наличия экрана или модели.

## Компоненты

| Компонент | Назначение | Граница доверия |
| --- | --- | --- |
| `apps/web` | React, TypeScript, Vite, TanStack Query, мобильная навигация и графики | Весь ввод клиента недоверенный |
| `backend/nox` | FastAPI, схемы входа, сервисы, SQLAlchemy-модели, проверка прав | Сервер принимает решение о каждом доступе |
| Telegram adapter и bot handlers | Aiogram, Bot API, команды и входящие сообщения | Права Telegram проверяются отдельно от локальной роли |
| PostgreSQL | Чаты, участники, сессии, наказания, аудит, правила | Единственный источник постоянных данных в production |
| Redis | Краткоживущие ограничения и защита от повторного обмена `initData` | Недоступность не должна отключать защиту production |
| Alembic | Версионирование схемы | Миграции выполняются управляемо перед запуском новой версии |
| Nginx в web-контейнере | Статические файлы и проксирование `/api` | TLS завершается на внешнем reverse proxy |

SQLite поддерживает лёгкий demo-запуск и изолированные тесты. Он не подтверждает поведение блокировок, SQL и конкуренции PostgreSQL. Production-конфигурация требует PostgreSQL через asyncpg.

## Аутентификация и права

Mini App передаёт исходную строку Telegram `initData` на backend. Сервер ограничивает размер и структуру, исключает дубли параметров, проверяет HMAC и время, извлекает типизированного пользователя. В production fingerprint проверенных данных атомарно потребляется в Redis. Только затем выдаётся короткоживущая непрозрачная сессия; в БД хранится хеш токена.

Сессия отвечает на вопрос о личности, но не о правах в чате. Для каждого chat-scoped действия сервер получает членство и внутреннюю роль. При реальном административном действии проверяются права в Telegram и возможности бота. Клиентские `user_id`, `chat_id` и `role` не могут предоставить доступ сами по себе.

Demo-вход предназначен для синтетического владельца синтетического чата и запрещён в production. Demo Telegram adapter не отправляет запросы в настоящий Telegram. В интерфейсе это окружение должно быть явно обозначено.

## Путь административного действия

1. Контроллер или Telegram handler валидирует команду и обращается к общему сервису.
2. Сервис проверяет доступ к чату, разрешение, целевого участника и права бота.
3. Постоянный ключ идемпотентности связывает запрос с одним делом; повтор с другим содержимым отклоняется.
4. Дело создаётся со статусом `pending`; внешний Bot API вызывается через отдельный adapter с таймаутом.
5. Подтверждённый результат меняет статус на `applied`, явный отказ — на `failed`, неоднозначный сетевой исход — на `unknown`. Изменение фиксируется в аудите.
6. Ручная отмена проходит собственный переход состояния и внешний обратный вызов. Временные ban/mute передают Telegram нативный `until_date`; после срока worker меняет локальные метаданные на `expired`, не отправляя запоздалый unban/unmute, который мог бы снять новое ограничение другого администратора.

Telegram и PostgreSQL не имеют общей транзакции. Поэтому обещать exactly-once для внешнего сетевого эффекта нельзя. Ключи, состояния и консервативная обработка `unknown` ограничивают повтор; вмешательство оператора может потребоваться при неоднозначном исходе. Запрещено отмечать такой исход как успех ради удобства интерфейса.

## Хранение

Основные отношения: пользователь принадлежит множеству чатов через `chat_members`; роль ограничена чатом. Дело ссылается на чат, целевого пользователя и инициатора. Апелляция ссылается на дело. Журнал хранит автора, действие и время. Правила Studio и история выполнения связаны уникальным ключом события. Входящие updates имеют устойчивый идентификатор для дедупликации.

Внешние ключи, уникальные ограничения и индексы дополняют проверки сервисов. Транзакции должны быть короткими: не следует удерживать глобальную блокировку во время медленного сетевого вызова. Конкуренция проверяется отдельно для PostgreSQL. Для одного участника и типа ban/mute допускается одно активное ограничение; перед заменой необходимо отменить текущее, иначе возвращается конфликт.

Worker очищает журналы Shield и Audit по `privacy_retention_days` чата, удаляет исходные payload завершённых updates и не исполняет устаревшие pending updates. Минимальные receipts с update ID сохраняются для дедупликации. История наказаний сохраняется для апелляций; параметр срока журналов не удаляет всю историю пользователя. Для архивирования receipts и выполнения запросов на удаление нужна отдельная эксплуатационная политика.

Реальный режим не должен использовать `create_all` как замену миграциям. Alembic задаёт историю схемы; резервные копии и проверка восстановления являются частью эксплуатации.

## Shield, Intelligence и Studio

Быстрые фильтры обрабатывают вход прежде дорогого анализа. Срабатывание хранит модуль и наблюдаемую причину. Эвристика не считается доказательством нарушения. Массовое вступление не должно автоматически наказывать всех новых участников.

AI-provider выделяется за интерфейс и по умолчанию отключён. Его отказ не должен отключать обычные фильтры. До подключения провайдера нужны бюджет, минимизация текста, условия хранения и допустимые действия с порогами уверенности. Наличие интерфейса не означает доступность облачной или локальной модели.

Studio использует ограниченную схему `trigger → conditions → action`. Конфигурация не является Python/JavaScript-кодом. Реальный исполнитель `automation_runtime.py` поддерживает `member_join → welcome`, `flood → delete/mute` и `warnings → mute`, учитывает приоритет и порог, резервирует запись выполнения с уникальным ключом события до внешнего эффекта и повторно проверяет права автора правила. Обработчики Telegram и сервис предупреждений передают в него события. Демо-доставка помечается `demo`; `unknown` не повторяется автоматически.

Preview не выполняет реальное наказание. Исполнитель не порождает рекурсивные события; число рассматриваемых правил ограничено. Перед добавлением нового действия необходимо проверить разрешения, идемпотентность и защиту от циклов. Планировщик ночных ограничений и произвольный граф правил не входят в текущий поддержанный набор.

## Клиент и дизайн

Дизайн NOX использует тёмные поверхности `#090B11`, `#111520`, `#1A2030`, акценты `#8585FF` и `#63D6E8`, контрастный текст и ограниченную анимацию. Навигация адаптируется к мобильному экрану; данные получают через TanStack Query. Telegram SDK вызывается после проверки доступности соответствующего API.

Проверяемые состояния страницы: загрузка, данные, пустая выборка, ошибка, истёкшая сессия и недостаточно прав. Кнопка не должна обещать действие, которого нет в API. Демо-аналитика явно отделяется от собранных данных реального чата.

## Масштабирование и измерения

Сначала измеряются время HTTP-ответов, запросы БД, длительность Bot API и очередь updates. Целевые задержки и фактические результаты публикуются в `docs/qa.md`; наличие async-кода не является бенчмарком. Rust/PyO3 не входит в обязательный путь этой версии: отдельный CPU-модуль оправдан только воспроизводимым профилем Python.

При росте нагрузки HTTP-процессы можно масштабировать за балансировщиком; общие сессии и replay guard находятся вне памяти процесса. Масштабирование worker допускается после проверки атомарного захвата задач, конкуренции и обработки восстановления. Извлечение микросервиса имеет смысл только при измеренной необходимости.
