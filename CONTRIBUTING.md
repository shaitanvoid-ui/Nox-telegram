# Участие в разработке NOX

NOX развивается как модульный монолит. Изменение должно сохранять общую модель прав доступа и одинаковое поведение API и Telegram-команд. Рабочие инструкции находятся в [документации разработки](docs/development.md), границы безопасности — в [SECURITY.md](SECURITY.md).

## Рабочий процесс

1. Создайте ветку от актуальной `main`, например `feat/report-review` или `fix/expired-mute`.
2. Опишите пользовательский сценарий, его ограничения и критерии проверки.
3. Реализуйте одну законченную возможность. Если внешний сервис недоступен, верните понятную ошибку; не заменяйте её сообщением об успехе.
4. Добавьте проверки критичных ветвей: доступ к чужому чату, повторный запрос, отказ Telegram, истёкшая сессия, конкурирующая запись.
5. Выполните соответствующие проверки из `docs/development.md` и приложите фактические результаты к pull request.
6. Создайте понятный коммит: `feat: add appeal review`, `fix: reject replayed init data`, `test: cover webhook retries`.

Не переписывайте чужую историю, не используйте force push для `main` и не публикуйте production без разрешения владельца.

## Границы модулей

- HTTP-контроллеры и Telegram handlers валидируют вход и вызывают сервисы. Они не содержат самостоятельных реализаций наказаний или проверки прав.
- Сервисы определяют переходы состояний и границы транзакций. Постоянные данные хранятся в PostgreSQL; Redis не заменяет базу.
- Клиент получает разрешения от backend. Скрытая кнопка не считается контролем доступа.
- Интеграция Telegram отделена от модели наказаний: подтверждённая доставка, ошибка и неоднозначный результат различаются.
- Моки используются только в тестах или явно обозначенном demo-окружении.

## Качество кода

Python-код должен проходить Ruff, проверку типов и тесты. TypeScript работает в строгом режиме; для клиента обязательны линтер, проверка типов, компонентные тесты и сборка. Не ослабляйте проверки через широкие `ignore`, `any` или исключения без документированной причины.

Используйте небольшие модули с одной ответственностью. Асинхронный путь не должен выполнять блокирующий сетевой ввод-вывод. Не перехватывайте все исключения с последующим ложным успешным ответом. Пользовательские ошибки должны быть безопасны, а диагностические логи — полезны без секретов и содержимого частной переписки.

## Изменения схемы и API

Изменение SQLAlchemy-моделей сопровождается Alembic-миграцией. Проверьте обновление существующей базы; автогенерация не гарантирует безопасность удаления или переименования. Для потенциальной потери данных сначала разработайте перенос, резервное копирование и восстановление.

Не меняйте смысл опубликованного поля незаметно для клиента. Поддерживайте типы ответов, OpenAPI и документацию контракта. Для списков сохраняйте ограничение размера страницы и детерминированную сортировку. Для финансовых и административных действий продумайте идемпотентность до добавления кнопки.

## Проверка интерфейса

Проверьте мобильную навигацию, состояния загрузки, пустые списки, ошибки API и отсутствие разрешений. Минимальные ширины: 320, 360, 375, 390, 430 и 768 px; отдельно проверьте desktop. Учтите клавиатуру, Telegram safe areas, масштабирование текста и `prefers-reduced-motion`.

Все элементы, похожие на рабочие действия, должны работать либо объяснять причину недоступности. Demo-данные и неподключённые интеграции должны быть видимо обозначены.

## Секреты и лицензирование

Не добавляйте в Git токены Telegram, `.env`, ключи сессий, дампы БД, логи с персональными данными и screenshots с реальными участниками без необходимости. Используйте GitHub Secrets или секрет-хранилище окружения. При утечке сначала отзовите секрет; удаление строки новым коммитом не отзывает его.

Лицензия проекта пока не выбрана владельцем. Отсутствие `LICENSE` не предоставляет разрешение на публичное распространение; сторонние зависимости сохраняют собственные лицензии. Не добавляйте лицензию от имени владельца без его решения.
